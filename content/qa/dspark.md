## 用一句话说 DSpark 做了什么。

DeepSeek 的投机解码框架：用“并行骨干 + 轻量顺序头”的半自回归草稿模型提高后位接受率，再用校准过的置信度和一张引擎步速表，按负载动态决定每个请求验证几个草稿 token。部署在 DeepSeek-V4 上，相同吞吐下每用户快 57%–85%。

## 投机解码的每 token 延迟公式是什么？有哪些优化方向？

$L=(T_{\text{draft}}+T_{\text{verify}})/\tau$。方向：降低起草代价、提高每轮接受数 $\tau$、降低验证代价。自回归草稿 $T_{\text{draft}}\propto\gamma$；并行草稿起草便宜但 $\tau$ 受后位衰减限制；DSpark 同时改善 $\tau$ 和验证代价。

## 什么是 suffix decay 和 multi-modal collision？

并行草稿每个位置预测的是对前缀取平均的边缘分布，没有以已采样的前一个 token 为条件。当存在多种合理续写（“of course” / “no problem”）时，不同位置可能采自不同模式，拼出 “of problem”（multi-modal collision），导致越靠后接受率越低（suffix decay）。

## DSpark 的顺序头是什么？为什么开销很小？

在并行骨干给出的 logits $U_k$ 上加一个依赖前一个采样 token 的偏置：$\mathrm{softmax}(U_k+B(x_{k-1},\cdot))$。默认 Markov 头是低秩查表 $W_1[x_{k-1}]W_2$，$r=256$。它不需要再跑 transformer 层，所以草稿长度从 4 到 16，单轮延迟只增加 0.2%–1.3%。

## DSpark 的草稿模型怎么拿到目标模型的上下文？

KV injection：把目标模型若干层的隐状态拼接，经 $\mathrm{RMSNorm}(W_c[\cdot])$ 投影后拼进草稿模型每一层的 key/value。草稿和目标共享并冻结 embedding 与 LM head。

## DSpark 训练用了哪些损失？为什么 TV 权重最大？

$\mathcal L=0.1\,\mathrm{CE}+0.9\,\mathrm{TV}+1.0\,\mathrm{BCE}_{\text{conf}}$，都乘位置权重 $e^{-(k-1)/\gamma}$。单步接受率等于 $\sum\min(p^d,p^t)=1-\tfrac12\lVert p^d-p^t\rVert_1$，所以 TV 是接受率的直接代理；CE 只看一个样本 token。

## 置信度头预测的是什么？标签怎么来？

在前 $k-1$ 个草稿都被接受的条件下，第 $k$ 个被接受的概率。模型是 $\sigma(w^\top[h_k;W_1[x_{k-1}]])$，软标签 $c^*_k=1-\tfrac12\lVert p^d_k-p^t_k\rVert_1$，用 BCE 训练，不需要真的跑验证。

## 为什么要做 Sequential Temperature Scaling？

调度器把置信度连乘成前缀存活概率再求和，需要绝对数值准确。原始 ECE 3%–8%，连乘后误差放大。STS 从左到右为每个位置选温度，最小化累积乘积的 ECE，校准后约 1%；温度缩放单调，不改变排序。

## 写出 DSpark 调度器的优化目标。

$\Theta=\tau\cdot\mathrm{SPS}(B)$，其中 $\tau=\sum_r(1+\sum_{j\le l_r}a_{r,j})$ 是期望产出 token 数，$B=\sum_r(1+l_r)$ 是送进目标模型的 token 数，$a_{r,j}=\prod_{i\le j}c_{r,i}$，$\mathrm{SPS}(B)$ 是启动时测好的步速表。

## 为什么按 $a_{r,j}$ 全局降序贪心是合理的？

$a_{r,j}$ 关于 $j$ 单调不增，降序取一定先取请求的短前缀，前缀约束自动满足；每加一个 token，$\tau$ 恰好增加 $a_{r,j}$，所以在给定 $B$ 下贪心让 $\tau$ 最大。再在 $B$ 上找使 $\Theta$ 最大的点，单峰时遇到第一次下降即停。

## 贪心提前停止什么时候不是最优的？

$\Theta(B)$ 不单峰时。真实 SPS 是离散带锯齿的（CUDA Graph 档位、kernel 分块），可能在某个 $B$ 出现局部下降、之后又回升，提前停止就会错过后面的更优点。

## 动态验证长度会不会破坏投机解码的无损性？

本身不会。会破坏的是 anticipating 的决策：如果“验证到哪”依赖第 $k$ 个及之后位置的采样结果，就把未来信息混进了接受与否的决定。DSpark 的 $c_{k+1}$ 依赖采样的 $x_k$，所以全局回溯搜索会出问题；按前缀顺序贪心、提前停止的版本是 non-anticipating 的。

## 生产里 DSpark 怎么和零开销调度（ZOS）兼容？

ZOS 要求在当前步结束前确定下一步的 batch 大小，所以用两步之前的置信度估计容量 $K$，当前步再按累积置信度选 top-$K$；同时去掉提前停止以绕开 SPS 锯齿。论文称截断长度只依赖两步前的信息，形成“因果屏障”，因而仍无损（论证而非证明）。

## 为什么固定阈值的自适应验证不够好？

阈值不感知负载：低负载时验证几乎免费，阈值让你少验证；高负载时验证昂贵，同一阈值又验证太多。DSpark 的隐式阈值是“边际接受概率 = SPS 下降造成的损失”，随负载移动。论文的静态阈值扫描也显示不同领域的最佳阈值差异很大。

## DSpark 离线实验比 Eagle3 和 DFlash 提升多少？

关掉调度器比草稿质量，接受长度宏平均：Qwen3-4B/8B/14B 上比 Eagle3 高 30.9% / 26.7% / 30.0%，比 DFlash 高 16.3% / 18.4% / 18.3%。另外 2 层 DSpark 就超过 5 层 DFlash。

## 生产线上效果怎么表述最准确？

对照线上 MTP-1：相同吞吐下每用户速度 V4-Flash +60%–85%、V4-Pro +57%–78%；宽松 SLA 下聚合吞吐 +51% / +52%。严格 SLA 下的 +661% / +406% 是基线接近不可用时的名义值。中等负载每请求验证 4–6 个 token，负载升高时平滑下降。

## 为什么静态的 MTP-3 / MTP-5 在高并发下反而降低吞吐？

高并发时目标模型 decode 不再是纯访存受限，每个额外验证 token 都占 batch 容量。固定验证 3–5 个 token，大量低存活概率的后缀 token 挤掉了其他请求的位置，净效应为负。

## DSpark 有哪些局限？

起草代价固定，低接受率请求也要付 $\gamma$ 个位置的骨干前向；提前停止的最优性依赖单峰；生产无损性是论证而非证明；生产栈（内部框架、kernel、服务配置）不可从开源的 DeepSpec 完全复现。

## AdaSpark 在 DSpark 基础上改了什么？

在线学习验证耗时（不再离线测 SPS、不再单独校准），用 DSpark 的置信度头作为输入来排序和确定树形验证的大小，并把请求自身文本的 n-gram 续写加入候选。声称比 DSpark 再快 1.5×–3.1×（作者自述）。
